# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run tauri dev      # run the desktop app (Rust shell + Vite dev server)
npm run build           # tsc + vite build -> dist/ (the Tauri app only)
npm run build:viewer    # vite build --config vite.viewer.config.ts -> dist-viewer/ (the public viewer only)
```

There is no test suite yet (deliberate — not yet decided what's worth testing here).

`tsconfig.json` has `noUnusedLocals`/`noUnusedParameters` on — an unused import or variable fails `npm run build` (not just a lint warning), so clean up as you go rather than leaving dead imports for later.

The Tauri app (`npm run build`) and the public viewer (`npm run build:viewer`) are two **separate** Vite builds (`vite.config.ts` vs `vite.viewer.config.ts`) from the same `src/`. Building one does not touch the other's output directory.

## Guiding principle: reuse over duplication

This repo has two independent build targets (desktop app, public viewer) sharing one `src/`, which creates constant temptation to just paste a second copy of something instead of extracting it. Don't. Default to making things reusable — a shared function, a shared component builder, a shared CSS rule — rather than writing a second near-identical version. If you're about to duplicate logic, markup, or styling that already exists elsewhere in the repo, that's a sign to extract/reuse instead, not a sign to move faster.

Duplicating is only acceptable with a genuinely good reason (the two things are only superficially similar and will diverge, or a shared abstraction would need so many flags/branches it's less readable than two small copies) — and that reason should be stated in a comment or commit message, not just assumed. "It was faster this way" is not a good reason. See "Shared rendering between the desktop app and the viewer", "Shared panel chrome", "CSS sharing", and "Shared persistence" below for the concrete pattern this has already produced repeatedly in this codebase: split "compute/data" from "render/build," and share the render/build half even when the data half must stay separate.

## Architecture

### The three things in this repo

1. **Desktop app** (`src/main.ts` entry, `index.html`) — the actual Tauri app. Talks to a local `aw-server` and to the filesystem (goals/todos/settings persisted as JSON under `$APPDATA` via `@tauri-apps/plugin-fs`).
2. **Public viewer** (`src/viewer-main.ts` entry, `viewer.html`) — a static site, deployed to GitHub Pages, with no access to AW or the filesystem. Polls a remote API for whatever it needs to display.
3. **`valtown/houseSimulatorStatus.ts`** — a small HTTP val (pasted by hand into val.town's editor, not deployed from this repo) that the desktop app pushes to and the viewer polls. Pure data relay, no business logic — see "Why val.town is dumb" below.

### Scene rendering: one engine, two interactivity levels

`src/scene/renderer.ts` (`SceneRenderer`) builds the isometric scene — rooms, objects, camera panning, room-dimming focus, "currently doing X" overlay highlighting — with **no interactivity of its own**. It exposes two protected no-op hooks, `attachRoomInteraction`/`attachObjectInteraction`, that subclasses override:

- `src/scene/House.ts` (`House`) — the desktop app's view. Adds click handling, the object context menu, and calls into `src/aw/client.ts` to actually start/stop tracking.
- `src/scene/viewer.ts` (`HouseViewer`) — the public viewer's view. Room clicks and `navigate` actions (staircases) work the same as `House` — it's just looking around. Clicking an `activity` object only shows a floating text label with the object's name; it never calls anything AW-related, since the viewer has no AW access regardless.

Room/object data (`src/scene/rooms.ts`) and tileset variants (`src/scene/tileset.ts`) are shared, unmodified, by both.

### AW activity tracking (`src/aw/client.ts`)

Reuses aw-webui's own manual-stopwatch bucket (`general.stopwatch`, `data: {running, label}`) so tracked time shows up in AW's own UI too, not just this app's.

Hard-won correctness rules, each backed by a real bug this session:

- **Never use `client.heartbeat()` for periodic refresh.** It merges into the last event or inserts a new one based on whether the gap since the last call is under its `pulsetime` — and browsers/webviews throttle `setInterval` in backgrounded windows, which can silently stretch that gap past `pulsetime` and split one continuous session into two events. Every periodic tick instead calls `client.replaceEvent()` by the event's own known id, recomputing `duration` fresh from wall-clock time (`now - startedAt`) — correct regardless of how delayed a tick was, no merge-or-insert ambiguity possible.
- **`replaceEvent`/`insertEvents` both POST to the same `/events` endpoint**; whether it inserts or updates-in-place depends entirely on aw-server recognizing a pre-set `id` in the payload as "replace this." Confirmed empirically against a live server — it genuinely does update in place, but **only when the id is correct and already exists**. IDs are global across the whole aw-server instance, not scoped to one bucket — never use a placeholder/guessed id in a replace call, even in a throwaway test bucket, or you can silently clobber/relocate an unrelated real event elsewhere.
- **Only one House Simulator activity may be `running: true` at a time, enforced against AW directly, not just in-memory state.** The app no longer stops tracking when the window closes (an overnight sleep-tracking session should keep accruing time with the app shut), so a *different* activity being started is the actual moment something earlier needs closing out — and it may not be reflected in memory if the app just restarted. `startActivity()` checks AW's actual latest event, not just the local `current` variable, before beginning anything new.
- **`resumeActivity()` (called on launch) extends the still-running event's duration to real elapsed time, regardless of gap length** — it does not truncate after some timeout, and does not care if the app was closed for 10 seconds or 10 hours. This is deliberate: it's what makes leaving something "running" across an app restart meaningful (e.g. sleep tracking) instead of just a crash-recovery nicety.

### Goals

`src/goals/types.ts` defines `Recurrence` (`once` / `daily` / `weekly` / `monthly`-by-Nth-or-last-weekday, possibly multiple occurrences) and `Goal` (activity label + target minutes + recurrence + optional `skipDates`/`createdAt`/streak fields — see "Streaks" below). `src/goals/recurrence.ts`'s `isScheduledOn()` is the one function that decides "does this goal apply today" — it's imported directly (not duplicated) everywhere that needs it, including the viewer build.

AW only measures time per activity **label**, not per goal — so the UI (`src/goals/progress.ts`) groups all of today's scheduled goals by activity label and sums their targets before comparing against tracked time, rather than tracking progress per-goal. Re-adding a goal for the same activity + identical schedule extends the existing one's target instead of creating a duplicate (so "I practiced piano, finished my 1hr goal, then added another 30min" correctly un-finishes it rather than showing two cards).

**Streaks** (`src/goals/history.ts`), recurring goals only — a "once" goal has no repetition to streak. Deliberately *not* a raw incrementing counter: `Goal.streakStartDate` ("YYYY-MM-DD") anchors the current streak, and `Goal.highestStreak` is the only actual stored number (ratchets up, never resets). `getCurrentStreakLength(goal, history)` derives the current length on demand — just a count of that goal's `completed` entries on or after `streakStartDate` — rather than storing a second number that could drift out of sync with the history log. `updateStreak()` (called from `settleGoal()`'s existing day-by-day walk, so this piggybacks on settlement rather than needing its own pass) re-anchors `streakStartDate` to *today* on every loss, not just unsets it — a loss day being its own anchor still produces a correct 0-length read afterward, since the formula only counts *completed* entries, and the loss day itself never has that outcome. Goal objects are mutated in place (same pattern as `skipGoalToday`); `settleGoalHistory()` persists them via the new `persistGoals()` in `state.ts` only if a streak field actually changed. `goal.highestStreak` is just another field on the already-pushed `Goal` objects, so it reaches val.town for free — but a *current* streak can't be derived from that alone (it needs the full history log, which never leaves the desktop app — see "no All-Time Goals in the viewer" below). That's what `/api/streaks` is for: `getTodayStreaksByGoalId()` computes current streak length for today's scheduled goals (the desktop app has the history to do it), and `pushTodayStreaks()` pushes that map once per calendar day — same "static until the boundary changes" gating as `pushYesterdayStats`, since a streak only changes at settlement anyway. `formatStreak()` (the "Streak: 3 (best 7)" formatting, pulled out of `describeStreak()`) lives in `goals/ui.ts` rather than `goals/history.ts`, specifically so the viewer can call it too: `history.ts` imports `getDurationMinutes` from `aw/client.ts`, which would leak AW-client code into the viewer bundle if the viewer imported anything *runtime* from it (type-only imports, like `periodStats.ts`'s, are fine — this isn't one). Shown in the Goals Manage modal's row text, the desktop Dashboard's per-goal subrows, and the viewer's own Dashboard subrows (`buildDashboardBlock()` in `viewer-main.ts`, fed by `/api/streaks` + the `highestStreak` riding along on `/api/goals`) — three call sites, one `describeStreak()`/`formatStreak()` pair behind all of them.

### Three always-or-on-demand surfaces, split by time range

Status/progress UI is split across three places, deliberately divided by **time range + audience** rather than by data type (goals vs. activity):

- **Jacqueline panel** (`src/goals/panel.ts`, `buildFloatingPanel` title hardcoded to `CURRENT_USER_NAME`) — always visible, not closable, not draggable. Just "who's using the house, what they're doing right now, connection health" — no goal data here anymore.
- **Dashboard panel** (`src/dashboard/panel.ts`) — always visible, not closable, draggable. **One day at a time**: a date picker (defaulting to today) drives that day's goal progress + activity breakdown; `getGoalProgressForDate()`/`getActivityStatsForDate()` branch on whether the picked day is the real current day (live, "up to now") or a settled past/future day (plain midnight-to-midnight range query).
- **Statistic modal** (`src/dashboard/statisticModal.ts`) — opened on demand from the "Statistic" button. Two tabs: **All Time** (most completed/skipped activity, all-time activity pie) and **Period** (goal progress, most completed/skipped, and an activity pie — the same three kinds of stats, just scoped to one Weekly- or Monthly-sized window at a time, picked via a mode toggle + date anchor).

This came from Dashboard and Jacqueline originally overlapping (both showing goal info) and Dashboard itself originally being one tabbed panel mixing today-only and all-time data. If a new "status" need comes up, put it in whichever of these three already matches its time range rather than adding a fourth surface or reintroducing tabs — the overlap is what got fixed here. All-time stats are only computed when the Statistic modal is actually opened (`getActivityStats()` scans a much wider AW date range) — unlike Dashboard's queries, which legitimately re-tick every 30s *while viewing today* (a past/future day's data can't change, so the interval skips re-fetching once the picker has moved off today).

**The Dashboard date picker itself is desktop-app-only** (same reasoning as "no All-Time Goals in the viewer" below): it needs an arbitrary-range AW query per picked date, and the viewer never has AW access. It does, however, apply to the app's own mobile Dashboard tab for free, since that calls the exact same `setupDashboardContent()` the desktop panel does. The viewer's own Dashboard isn't stuck on *only* today, though — it gets a Today/Yesterday hyperlink toggle instead (`.day-link` in viewer-styles.css, viewer-only — the app's date input stays the real picker). "Yesterday" is whatever the app last pushed to `/api/yesterday` (`pushYesterdayStats()`, reusing `getActivityStatsForDate()` reshaped into a plain label→minutes map, same shape `/api/status` already pushes for today) — a settled day, so unlike "today" it never needs live-elapsed-time math added. Each toggle instance (desktop panel, mobile tab) owns its own day selection independently, same as the app's own per-instance date input (`viewer-main.ts`'s `buildDashboardBlock()`).

**The Statistic modal's Period tab (free-form date picker, Weekly/Monthly) is also desktop-app-only** for the same reason, but the viewer isn't left with *only* All Time — it gets its own Period tab fed from 4 fixed windows (This Week/Last Week/This Month/Last Month) that the desktop app precomputes and pushes to val.town (see `/api/period-stats` below), instead of a free date picker. Both Period tabs share the same compute layer (`dashboard/periodStats.ts`'s `computePeriodStats()`) and the same render functions (`renderGoalList`/`renderGoalOutcomes`/`renderAllTimeActivity`) and toggle-group UI (`ui/toggleGroup.ts`'s `buildToggleGroup()`, which is why that and `.day-toggle`/`.stat-tab*` CSS had to move from app-only into shared code once the viewer needed them too) — only the picker itself (free date vs. a fixed 4-option list) and where the data comes from (live AW query vs. whatever was last pushed) differ.

### Mobile: a separate UI tree, not a reflow

Below `@media (max-width: 700px) and (orientation: portrait)` (`shared-chrome.css`), the floating panels/top-buttons/floor-buttons give way to a bottom tab bar (Home/Dashboard/Statistic/Settings) + one full-screen page at a time. **Both UI trees are always built**, in both the desktop app and the viewer — this media query is the only thing deciding which is visible, so resizing or rotating across the breakpoint needs zero JS.

`src/ui/mobileTabs.ts`'s `setupMobileTabs()` is the shared tab-bar-plus-pages skeleton (zero Tauri/AW dependency, same as `buildFloatingPanel`/`buildModal`) — it only owns tab-switching, not what's on a tab. Each entry point (`main.ts`'s `setupMobileUI()`, `viewer-main.ts`) fills the four pages with the *exact same* `setupDashboardContent()`/`setupStatisticContent()`/`buildDisplaySettingsSection()` (or the viewer's own equivalents) their desktop panels/modals already use — a mobile tab is a full-screen instance of the same content function, not a second copy of it. This is also why every Dashboard/Statistic feature added since (the date picker, the Period tab, the Today/Yesterday toggle) applies to mobile for free without any mobile-specific code — see those features' own paragraphs above.

**Home is the one tab that isn't a panel/modal content function at all** — just bare stacked status text (name/current activity/last synced, no chrome) plus one FAB, so it doesn't cover the scene. `#mobile-page-home` ignores pointer events everywhere except its own direct children (the status text, the FAB), so taps still reach the Pixi canvas underneath for looking at the house. The FAB differs per build: the app's is "Pick Action" (`setupMobilePickAction()` in `main.ts`) — a flat modal list of every activity in `ACTIVITIES`, tapping one calls `House.toggleActivity(label)` (mirrors `runAction`'s start/stop/overlay/camera-focus logic but for a tap with no clicked object behind it) — letting you start/stop tracking without navigating to the right room/object, which matters more when screen space is scarce. The viewer's is "Leave a note" (`setupMobileMessageModal()`), a native-popup-style dialog standing in for the inline form that doesn't fit on Home — the viewer has no AW access to track anything regardless, so there's no action-picking equivalent for it.

**Room navigation (floor buttons) is dropped entirely on mobile, not just hidden** — the scene just auto-follows whatever's currently running (the same focus logic the desktop already has), and manual panning isn't worth the screen space below this breakpoint. This was a deliberate, explicit call for both the app and the viewer, not an oversight.

**Explicitly out of scope:** going further and making the mobile tabs literal `buildFloatingPanel`/`buildModal` instances (reusing chrome, not just content) was considered and declined — the win would've been smaller than the added complexity, and mobile pages already get the sizing/scrolling they need from `.mobile-page`'s own CSS (`overflow-y: auto`, full-bleed) without needing panel/modal resize semantics at all.

Building this surfaced an ordering problem worth remembering: `House`/`HouseViewer`'s constructor fires its `onRoomChange` callback synchronously for the initial room, before a caller building floor buttons *from* that callback would have anything to bind against yet. `src/ui/floorButtons.ts`'s `setupFloorButtons()` takes no arguments up front and returns `{ bindGoToRoom(fn), onRoomChange(name) }` instead — build the buttons first (a no-op `goToRoom` closure), construct `House`/`HouseViewer` passing `floorButtons.onRoomChange` as the room-change callback, *then* call `bindGoToRoom` once the instance exists. Solves the "doesn't exist yet" problem by reordering instead of papering over it with a deferred placeholder.

### Shared panel chrome (`src/ui/draggablePanel.ts`)

`buildFloatingPanel(title, { closable?, draggable?, className? })` is the one implementation behind Jacqueline's and Dashboard's header/body/drag chrome — both default to `true` for `closable`/`draggable`; Jacqueline overrides both to `false` since it always lives in the same corner and is never meant to be dismissed. It's plain DOM code with zero Tauri dependency, so **the viewer imports and calls it directly** (`viewer-main.ts`) instead of re-implementing a lookalike — the viewer's Jacqueline and Dashboard panels are the literal same component as the desktop app's, not a visually-similar copy.

Dragging is done via a dedicated grip-icon button in the header (`.floating-panel-drag-handle`), not the whole header — grabbing the title text to move the panel used to fight with just trying to read it. The grip icon itself is drawn with CSS `box-shadow` (a 2×3 dot grid), not a Unicode glyph — a glyph's availability/rendering varies by platform font, a CSS shape doesn't.

`headerExtra?: HTMLElement` lets a caller drop one arbitrary element into the header (left of the drag handle, right of the title) instead of hand-rolling a second header-ish row inside the body — the Dashboard panel's date picker uses this to live in the header, while the same content function's mobile-tab caller (no header at all there) falls back to an inline copy in the body instead. See `setupDashboardContent`'s `providedDateInput` parameter in `src/dashboard/panel.ts` for the pattern: build the control once, optionally hand it to `buildFloatingPanel` as `headerExtra`, and pass the same element into the content function so it drives the same rendering either way.

**`buildModal`'s dialog/header/body now mirror `buildFloatingPanel`'s structure exactly** (pinned header via `flex-shrink: 0`, scrolling body via `flex: 1; min-height: 0`, same `resize`-grip-vs-scrollbar `padding-bottom` fix on `.modal-dialog.resizable`) — they used to differ (the whole modal dialog scrolled as one unit, header included, and its title text/padding were plainer than the panel's). Only `width` is still legitimately per-build (`styles.css`/`viewer-styles.css` each have a one-line `.modal-dialog { width: ... }` override); everything else moved into `shared-chrome.css`'s `.modal-dialog`/`.modal-header`/`.modal-body` once the two builds' versions became byte-identical.

### Shared rendering between the desktop app and the viewer

The viewer and the desktop app need to show the *same* sections (Dashboard's Today's Goals/Today's Activity, the Statistic modal's All-Time Activity, Jacqueline's current-activity/sync-status) but get their data from fundamentally different sources — the desktop app queries AW directly, the viewer only has whatever was last polled from val.town plus client-side live-elapsed math. The fix was splitting "compute the data" (stays separate per surface) from "render the data to DOM" (shared) — and, where the UI chrome itself has no data dependency at all (the panels themselves, not their contents), just calling the exact same builder from both (`buildFloatingPanel`/`buildModal`) rather than maintaining two copies of a "static HTML + manual rendering" pattern. The viewer used to render its Jacqueline/Dashboard/Stats content into one static sidebar `<div>` defined in `viewer.html`; it now builds its panels and modal entirely in `viewer-main.ts`, the same way the desktop app's `index.html` only has `#status`/`#room-label`/`#app` and everything else is built in `main.ts`.

- `src/goals/goalGroups.ts`'s `groupGoalsForDate()` — the one goal-grouping-by-label implementation, for any date (not just today, despite the file's original name) — it also now excludes goals whose `createdAt` is after the date in question, so a past date's view doesn't show a goal that didn't exist yet back then. Before the first version of this, `goals/progress.ts`, `dashboard/panel.ts`, and `viewer-main.ts` each independently re-derived the same grouping.
- `src/dashboard/render.ts` — `buildDashboardSections()`/`renderGoalList()`/`renderActivityList()` for the Dashboard panel, `renderAllTimeActivity()` (pie + legend, capped to top 5) for the Statistic modal's activity sections (All Time and Period both), and `renderGoalOutcomes()` (the "Most completed"/"Most skipped" rows) for the same modal's All Time *and* Period tabs plus the viewer's own Period section. Called by both `dashboard/panel.ts`+`dashboard/statisticModal.ts` (fed by local AW queries / `getGoalHistory()`) and `viewer-main.ts` (fed by whatever's currently polled from val.town — `/api/status`/`/api/goals`/`/api/stats`/`/api/period-stats`/`/api/yesterday`/`/api/streaks` — plus `startedAt`-based live elapsed, same trick used elsewhere).
- `src/status/render.ts` — `renderCurrentActivity()`/`renderSyncStatus()` for the Jacqueline panel's content, plus the shared `CURRENT_USER_NAME` constant so the one hardcoded name lives in one place. `renderSyncStatus`'s `showAw` flag is why the viewer never shows an "AW: Connected"/"Disconnected" line at all — it has no AW access full stop, not merely "currently disconnected."

**The viewer's Statistic modal has no "All-Time Goals" section** — unlike the desktop app's. The full goal completion/skip history (`getGoalHistory()`) stays local-only and nothing pushes all of it to val.town; the viewer's All Time tab only ever gets activity stats (`/api/stats`). Its Period tab is the exception — it does get most-completed/skipped *outcomes*, but only ever for the 4 fixed windows in `/api/period-stats`, computed from a `getGoalHistory()` filtered to that window at push time, not the raw log itself. Don't try to fake full history by inferring completion from `/api/goals` + `/api/status` — the whole point of the history log is tracking outcomes over time, which isn't reconstructable from "what's the goal definition + today's minutes."

**CSS sharing: `src/shared-chrome.css`, imported by both.** `styles.css` and `viewer-styles.css` are still two independent Vite entry stylesheets, but Vite resolves a local `@import` fine in both builds — so every rule confirmed byte-identical between the two (the theme palette, `.floating-panel*`, `.goal-row`/`.dashboard-row`/etc., `#floor-buttons`/`#top-buttons`, ...) lives in `shared-chrome.css` and gets `@import`ed, instead of being hand-copied into both files. A rule stays local to one stylesheet only when it's *legitimately* different per build (e.g. `.modal-dialog`'s width, `.settings-checkbox-row`'s margin) — if you're about to paste a new rule into both files identically, it belongs in `shared-chrome.css` instead. If you add a new shared-rendering class in `render.ts`/`draggablePanel.ts`/`modal.ts` and only style it in one of the two stylesheets, check whether it should go in `shared-chrome.css` rather than get duplicated (or left unstyled in the other build).

One function's scope quietly broadened for this: `getTodayMinutesByLabel()` (`src/goals/progress.ts`) used to only cover activities that had a goal attached (its one caller was the goal-progress calc). It now covers every entry in `ACTIVITIES`, because the viewer's Today's Activity list needed full parity with the desktop Dashboard's — not just whatever happened to have a goal.

### Shared persistence (`src/lib/`)

`jsonFileStore.ts` (load/save a JSON file under `$APPDATA`) and `persistedState.ts` (in-memory value + change-listener `Set`, backed by a store) are the two pieces every feature's `state.ts`/`store.ts` is built from (goals, todos, settings). Reuse these for any new local-persisted domain rather than copy-pasting a fourth near-identical pair.

### Broadcasting: why val.town is deliberately dumb

The viewer can never reach the local `aw-server` directly — it's a separate static site, possibly on a different machine. So *something* local has to combine goal targets with tracked time and publish the result; `val.town` only stores and forwards independently-pushed blobs, each on its own cadence:

- **Goal definitions** (targets + schedules, not progress) — pushed whenever goals change (`onGoalsChange` → `pushGoals()`), independent of activity changes, so editing a goal reaches the viewer immediately instead of waiting for the next activity switch.
- **Today's tracked minutes per activity label**, *excluding* whatever's currently running — pushed on activity change (`onActivityChange` → `pushStatus()`) and once at startup. Nothing is re-pushed on a timer.
- **All-time per-activity totals + rolling daily averages** (`pushStats()`, backing `/api/stats`), **the 4 fixed This Week/Last Week/This Month/Last Month windows** (`pushPeriodStats()`, backing `/api/period-stats`), **yesterday's tracked minutes per label** (`pushYesterdayStats()`, backing `/api/yesterday`), and **today's scheduled goals' current streak length, by goal id** (`pushTodayStreaks()`, backing `/api/streaks`) — all four scan more AW history (or, for streaks, more of the history *log*) than `pushStatus`'s today-only query, so they share one slow hourly timer (startup + `setInterval`, see `main.ts`) instead of piggybacking on activity/goal changes. None of the four get their own separate cadence: simpler than tracking day/week/month boundaries directly in the scheduler, and This Week/This Month genuinely want hourly freshness since they change through the day. The *static* ones — Last Week, Last Month, yesterday, and today's streaks — instead self-skip the expensive part once nothing could have changed: `pushYesterdayStats`/`pushTodayStreaks` each track which "today" they last successfully pushed for and no-op on repeat calls within the same day (only advancing that tracker on a successful push, so a transient val.town outage still retries); `computeFixedPeriodStats()` caches Last Week/Last Month in memory keyed by that window's own start date, and only redoes the AW query once the cached start date no longer matches. All these caches are in-memory only, not persisted — an app restart recomputing once is a reasonable resync, not something worth avoiding. Either way the full push still happens every hour (val.town doesn't need its own staleness logic); only the local AW querying is what gets skipped.

For today's goal progress, the viewer joins the first two blobs itself — computes "is this goal scheduled today," sums targets by label, and adds the *live* elapsed time for whichever label matches the currently-running activity (the same `startedAt`-based client-side math as its "Running for X" clock). This is why val.town never needs to recompute anything when a goal is edited or time passes: both halves are always independently fresh, and the join is cheap and stateless on the client. The period stats are different: val.town stores exactly what `computeFixedPeriodStats()` already computed app-side (goal progress + outcomes + activity totals per fixed window) — there's no further joining for the viewer to do, since there's no live "running" session's elapsed time to merge into a past or fixed-boundary window the way there is for "today."

**A real backend (with actual computation/joins) was deliberately rejected** for this — see the conversation history around "do we need a second backend" if resurrecting that question; the conclusion was that AW-local-only data makes a smarter backend not actually solve anything a dumb relay doesn't.

**Dead end, don't retry:** serving the actual Pixi-rendered viewer directly from val.town (so val.town alone would be the whole public site, no GitHub Pages needed) was tried and reverted — val.town caps a val's own source at **80,000 characters**, and a bundled Pixi app is several hundred KB even minified. Not a tuning problem; the viewer needs real static hosting (GitHub Pages).

**Schema migration gotcha:** val.town's `ensureSchema()` uses `CREATE TABLE IF NOT EXISTS`, which is a no-op once a table already exists in the live val's database — it does **not** retroactively add new columns. Any future change to an existing table's shape needs an explicit `ALTER TABLE ... ADD COLUMN` (wrapped in a `.catch(() => {})`, since it only fails if the column's already there) alongside updating the `CREATE TABLE` statement for fresh deployments. This bit us once already (a renamed column silently never existed on the live table, so every status push was failing with no visible error — see `pushStatus`'s `res.ok` check below).

**Never trust `fetch()` resolving as "it worked."** `fetch()` only rejects on network-level failures — an HTTP error response (e.g. the 500 from the schema bug above) resolves completely normally. `src/broadcast/client.ts` explicitly checks `res.ok` and tracks last-success/last-error, surfaced as the "VT: Synced ..." half of the Jacqueline panel's status line (the one place in the app that's always visible without opening devtools) — and, symmetrically, as the viewer's own "VT: Synced ..." line for its last successful *poll* rather than push (see "Shared rendering" below).

### GitHub Pages deployment (`.github/workflows/deploy-viewer.yml`)

Builds and deploys only `dist-viewer/` on every push to `main` — the desktop app's own source is never published. Two things that would silently break if "fixed" without understanding why:

- `vite.viewer.config.ts` sets `base: "/jacqueline-house-simulator/"` — GitHub Pages serves a project repo from that subpath, not domain root. Every texture path in `rooms.ts` is a root-relative string (`/objects/piano_base.png`) baked in long before Pages was a consideration; `src/scene/renderer.ts`'s `assetUrl()` helper routes every one of them through `import.meta.env.BASE_URL` so they resolve under the subpath. (`BASE_URL` is `/` for the Tauri app's own build — this is a no-op there.)
- `npm run build:viewer` renames the build output from `viewer.html` to `index.html` as a second step. Can't just name the *source* file `index.html` — the Tauri app's own entry already owns that name at the repo root — but Pages needs `index.html` specifically to serve the bare directory URL (`/jacqueline-house-simulator/`) instead of 404ing while `/jacqueline-house-simulator/viewer.html` works fine.
