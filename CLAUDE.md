# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run server          # run the Node server (tsx watch server/index.ts) — AW/SQLite/val.town owner, required for the app to do anything
npm run tauri dev       # run the desktop app (Rust shell + Vite dev server) — connects to npm run server over WebSocket
npm run build            # tsc + vite build -> dist/ (the Tauri app only; also what the Node server serves to plain browsers, see "The Node server" below)
npm run build:viewer     # vite build --config vite.viewer.config.ts -> dist-viewer/ (the public viewer only)
npm run build:admin      # vite build --config vite.admin.config.ts -> dist-admin/ (the admin tool only, see "Admin tool" below)
npm run typecheck:server # tsc --noEmit -p server/tsconfig.json
```

There is no test suite yet (deliberate — not yet decided what's worth testing here).

`tsconfig.json` has `noUnusedLocals`/`noUnusedParameters` on — an unused import or variable fails `npm run build` (not just a lint warning), so clean up as you go rather than leaving dead imports for later. `server/tsconfig.json` has the same settings, checked separately via `npm run typecheck:server` — it deliberately has no `"DOM"` lib (see "The Node server" below), so don't assume a clean `npm run build` means the server half type-checks too, or vice versa.

The Tauri app (`npm run build`), the Node server (`npm run server`), the public viewer (`npm run build:viewer`), and the admin tool (`npm run build:admin`) are four **separate** builds from the same `src/` (`vite.config.ts` / `server/tsconfig.json` via `tsx` / `vite.viewer.config.ts` / `vite.admin.config.ts`). Building or running one does not touch another's output directory.

## Guiding principle: reuse over duplication

This repo has four independent build targets (desktop app, Node server, public viewer, admin tool) sharing one `src/`, which creates constant temptation to just paste a second copy of something instead of extracting it. Don't. Default to making things reusable — a shared function, a shared component builder, a shared CSS rule — rather than writing a second near-identical version. If you're about to duplicate logic, markup, or styling that already exists elsewhere in the repo, that's a sign to extract/reuse instead, not a sign to move faster.

Duplicating is only acceptable with a genuinely good reason (the two things are only superficially similar and will diverge, or a shared abstraction would need so many flags/branches it's less readable than two small copies) — and that reason should be stated in a comment or commit message, not just assumed. "It was faster this way" is not a good reason. See "Shared rendering between the desktop app and the viewer", "Shared panel chrome", "CSS sharing", and "Shared persistence" below for the concrete pattern this has already produced repeatedly in this codebase: split "compute/data" from "render/build," and share the render/build half even when the data half must stay separate.

## Architecture

### The five things in this repo

1. **Node server** (`server/`, entry `server/index.ts`) — a plain Node process, meant to run 24/7 on a home server, not inside Tauri at all. The sole owner of AW access, goal/todo/settings persistence (SQLite), and derived stats; the only thing that pushes to val.town. Also owns rooms/objects/activities/object types/floors/characters (see "Rooms, floors, and connections" and "Characters" below) and a small mock workout mirror (`server/workouts.ts`, `src/workout/modal.ts` — hand-seeded sessions/sets, no real wger integration yet, independent of AW/goals). See "The Node server" below.
2. **Desktop app** (`src/main.ts` entry, `index.html`) — the Tauri app. No longer talks to `aw-server` or the filesystem directly — it's a thin client that opens one WebSocket to the Node server (`src/client/remoteState.ts`) and renders whatever that connection gives it. The exact same `dist/` build this produces is also what the Node server serves to a plain browser (see "One build, two delivery mechanisms" below) — Tauri's own role here is really just "cross-platform shell for the Pixi scene," not a privileged access point.
3. **Public viewer** (`src/viewer-main.ts` entry, `viewer.html`) — a static site, deployed to GitHub Pages, with no access to AW, the filesystem, or the Node server. Polls val.town for whatever it needs to display — still the only genuinely *view-only* surface (every WebSocket client, Tauri build or plain browser, gets full read/write). Supports multiple characters now (see "Characters" below): `/api/all` returns every `publish_to_viewer`-opted-in character's data keyed by id, and a character-picker modal (opened from the mobile Home tab's clickable name) lets a visitor switch who they're looking at. `CURRENT_USER_NAME` (`src/status/render.ts`) is only a fallback now — the initially-selected character (last-picked via `localStorage`, else a character literally named "Jacqueline," else whichever came first) — not a hardcoded single-user assumption anymore.
4. **Admin tool** (`src/admin-main.ts` entry, `admin.html`) — a separate static site served by the Node server at `/admin/`, for managing characters/activities/object types/rooms (including floors and connections). See "Admin tool" below.
5. **`valtown/houseSimulatorStatus.ts`** — a small HTTP val (pasted by hand into val.town's editor, not deployed from this repo) that the Node server pushes to and the viewer polls. Pure data relay, no business logic — see "Why val.town is dumb" below.

### Scene rendering: one engine, two interactivity levels

`src/scene/renderer.ts` (`SceneRenderer`) builds the isometric scene — rooms, objects, camera panning, room-dimming focus, "currently doing X" overlay highlighting — with **no interactivity of its own**. It exposes two protected no-op hooks, `attachRoomInteraction`/`attachObjectInteraction`, that subclasses override:

- `src/scene/House.ts` (`House`) — the desktop app's view. Adds click handling and the object context menu; starting/stopping tracking is a fire-and-forget `sendCommand("startActivity"/"stopActivity", ...)` to the Node server over `src/client/remoteState.ts`, not a direct call into `src/aw/client.ts` anymore (that file now runs server-side only — see "The Node server" below).
- `src/scene/viewer.ts` (`HouseViewer`) — the public viewer's view. Room clicks and `goTo` actions (staircases) work the same as `House` — it's just looking around. A click on an object with `activity` actions never calls anything AW-related (the viewer has no AW access regardless) — same as `House` peeking at someone else's object, see "Object actions" below.

Room/object data (`src/scene/rooms.ts`) and tileset variants (`src/scene/tileset.ts`) are shared by both — rooms/objects/activities/object types are no longer static compile-time data, though (see "Rooms, floors, and connections" below): both `House`/`HouseViewer` read whatever the Node server most recently pushed, the same live-module-binding pattern `setRooms()`/`setActivities()`/`setObjectTypes()` use elsewhere.

**Object actions** (`ObjectAction`, `src/scene/rooms.ts`): `{kind:"activity", activityId}` or `{kind:"goTo", roomId}` (a staircase — jumps the view, no AW tracking). By `activityId`/`roomId`, not a label/name, so renaming either via the admin tool cascades instead of orphaning a string baked in at authoring time. There's deliberately no `"view"` kind — every click recenters the camera on whatever was clicked unconditionally, so "just look at this" is simply the baseline behavior for an object with zero actions, not an assignable one. A single action runs directly on click; 2+ opens a shared picker (`src/ui/actionPicker.ts`'s `openActionPicker`, left- or right-click in `House`) with labels from `src/scene/actionDispatch.ts`'s `describeAction()` — one place resolving an activity id/room id to its display label, instead of `House.ts`/`viewer.ts` each re-deriving it. `House`'s own menu adds one more UI-level-only entry, "View" (peek at whoever else is currently attributed to one of the object's activity actions), constructed on the fly from attribution rather than a persisted action — the viewer has no such concept since it never tracks anything.

**Per-character animated overlays**: a `SpriteLayer` (object type's `overlay`) can carry a `spriteKey` + optional `frameCount`/`frameDurationMs` instead of a fixed `texture` — `src/scene/characterSprites.ts`'s `characterSpritePath(spriteName, spriteKey)` resolves it to `/characters/<spriteName>_<spriteKey>.png` for whoever's currently attributed to the activity, falling back to `DEFAULT_SPRITE_CHARACTER` ("jacqueline")'s own art if that specific file doesn't exist. Multi-frame playback slices one spritesheet left-to-right (`renderer.ts`'s frame-slicing helper, frame width/height derived from the sheet's own natural size, not authored) and advances on a per-sprite ticker in `tick()`. Reusable named overlays live in their own `sprite_overlays` table (`server/spriteOverlays.ts`, `SpriteOverlayDef`) rather than inline per-object-type JSON, so multiple object types can reference the same overlay by id instead of duplicating the blob; position offset stays per-object-type (`object_types.overlay_offset_x/y`) since the same overlay can want different placement on different furniture.

**Focused-room visual cue**: the currently-viewed room raises (`ROOM_RAISE_PX`, eased via `ROOM_FOCUS_EASE`, not an instant snap) and gets a soft blurred ambient glow behind its floor silhouette (`GLOW_COLOR`/`GLOW_ALPHA`/`GLOW_BLUR_STRENGTH`) — a filled-then-blurred copy of the same shape, not a crisp outline. No scale/grow effect — tried and fully removed (`isRoomFocusEffectsEnabled()` gates both off for `AdminPreviewRenderer`, whose own `moveRoom()` drives room position directly and would otherwise fight the raise easing). Front walls (the two edges facing the camera) dim to `FRONT_WALL_FOCUSED_ALPHA` specifically for the viewed room, since they paint above objects/overlays there and would otherwise block the view.

**Room depth-sort** (`compareRoomDepth`, module-level function in `renderer.ts`): rooms are drawn in an order derived from comparing their real `(u,v)` grid footprint RANGES (via `screenToGrid`, the exact inverse of `gridToScreen`) — v-range overlap first, then u-range as a tiebreaker, falling back to center-depth only for a genuine `(u,v)` overlap (shouldn't happen in a sane layout). No single derived scalar (origin y, farthest-corner y, center y) can correctly order two rooms whose SCREEN footprints visually overlap in general — this is why a real footprint-range comparison was needed instead.

**Room visibility** (`rooms.visible`, default `false`): a room + everything inside it only renders and is clickable when `visible` is true — by default only Jacqueline's Office, DDR Room, and Gym are. **Deliberately never read by `resolveRooms()`/`computeFloorMembership()`** — an invisible room still fully participates in floor-membership/position BFS for anything that connects to it; this is purely a render/input concern. `applyFocus()` reuses the same hide path (`container.visible = false; eventMode = "none"`) already used for a different-floor room, so an invisible room's objects (including character overlays) just don't render, and clicking through to them is impossible, while server-side activity tracking on an object inside it keeps running unaffected. `AdminPreviewRenderer` overrides `respectsRoomVisibility()` to `false` (same method-not-field pattern as `isRoomFocusEffectsEnabled()` below) so the admin tool can always see/edit a room regardless of what its `visible` flag is currently set to — that flag is exactly what's being edited there.

### Rooms, floors, and connections

Rooms, objects, activities, and object types all live in SQLite now (`rooms`/`objects`/`activities`/`object_types` tables, `server/{rooms,activities,objectTypes}.ts`), each with a plain serial `INTEGER PRIMARY KEY` id — no more hand-authored string/UUID ids. `STATIC_ROOM_SPECS`/`STATIC_ACTIVITIES`/`STATIC_OBJECT_TYPES` in `scene/{rooms,activities}.ts` are one-time seed sources only (`seed*IfEmpty()` on the server inserts their explicit small-integer ids verbatim) — not the runtime source of truth; `main.ts`/`viewer-main.ts` overwrite the mutable `rooms`/`ACTIVITIES`/`objectTypes` module bindings with server-fetched data right after connecting, before any room is built. `objects.id` is a single **global** serial id, not scoped to one room the way it used to be — a room's own placements no longer need admin-typed ids at all; the server assigns one on create.

**`rooms.level` is derived, never stored** — a room's floor is computed from which floor's connection-graph it belongs to (`computeFloorMembership()`), not a column you set. A floor (`scene/floors.ts`'s `Floor`, `floors` table) is just a `level` + a designated `baseRoomId`; a room connects to others via `connectedTo` (`ConnectedToEntry[]`, `room_connections` table) — `direction`/`gapTiles`/`lateralOffset` describing which edge of the *target* room the connection extends from (see `ConnectionDirection`'s own comment). Authoring convention is "a room only has to worry about what it connects to, not which room connects to it" — but see `resolveRooms()` below for why that convention doesn't mean only one side's entry is ever read.

**`resolveRooms(specs, floors)` has two completely different algorithms depending on whether `floors` is empty:**
- **Normal case (`floors` non-empty — the real game/viewer):** a BFS from each floor's base room (origin `(0,0)`) over the *undirected* connectedTo graph (same traversal `computeFloorMembership()`/`buildFloorTree()` use) positions every reachable room relative to whichever already-positioned room discovered it — using **whichever of the two rooms' entries links them**, regardless of which side declared it (`positionNeighbor()`: prefers the neighbor's own entry pointing back, otherwise inverts the known room's entry — flip direction to its `PAIR_DIRECTION`, negate `lateralOffset`, keep `gapTiles`; derived algebraically from the placement formula, not just asserted). **A room with no path back to any floor's base room is excluded from the result entirely** — not positioned at the origin and left overlapping whatever else is there, which is what used to happen (confirmed live: three real rooms were silently stacked at `(0,0)` before this was fixed). Cycles are harmless here, not an error — it's a plain BFS with a visited set, so a redundant edge in a loop just never gets used for position.
- **`floors: []` (admin-tool previews only):** the older per-room algorithm — each room walks up its own `connectedTo[0]` chain to whatever ancestor has none (defaulting to the origin), throwing on an actual cycle or a reference to a truly unknown room. The admin tool's isolated single-room editor and the room-connections modal's "room + synthesized neighbors" preview both rely on this specifically, since they have no real floor to BFS from.

**Per-room wall visibility**: `showLeftWall`/`showRightWall` (default `true`) on a room hide that side's default wall tiles entirely (`renderer.ts`'s `buildFloorAndWalls`) — a `wallOverrides` entry on a hidden side still renders (gap or replacement tile alike), since overrides are checked before the default-wall gate either way. `showBottomLeftWall`/`showBottomRightWall` (default `false`, the two edges facing the camera) render as a wall extension reusing the PARALLEL back wall's own tile style, not a dedicated corner piece — each is only ever touched by one wall run, so there's no shared corner joint to draw the way the back walls have. Resizing a room (cols/rows, admin-tool only, clamped to a 1×1 minimum) has no bounds-checking against its own objects' positions — objects were never clamped to the room footprint anywhere else in this engine either.

**`rooms.visible`** (default `false`) controls whether a room renders/is clickable at all — see "Room visibility" under "Scene rendering" above for the full behavior. Not something `STATIC_ROOM_SPECS` sets per-spec; the three default-visible rooms (Jacqueline's Office, DDR Room, Gym) are turned on by a one-time server-side backfill instead (`server/db.ts`'s `backfillDefaultVisibleRooms()`), same guarded-once-ever pattern as other column backfills in that file.

### AW activity tracking (`src/aw/client.ts`)

Lives under `src/`, not `server/`, purely because it has zero Tauri dependency and was reused verbatim rather than copied when the Node server took over AW access — **only `server/index.ts` and `server/rpc.ts` import it now**; nothing under `src/` (the desktop app) calls it directly anymore. Reuses aw-webui's own manual-stopwatch bucket (`general.stopwatch`, `data: {running, label}`) so tracked time shows up in AW's own UI too, not just this app's.

Hard-won correctness rules, each backed by a real bug this session — all still apply exactly as written below, just to the one long-running Node server process instead of to whichever Tauri window happened to be open:

- **Never use `client.heartbeat()` for periodic refresh.** It merges into the last event or inserts a new one based on whether the gap since the last call is under its `pulsetime` — and browsers/webviews throttle `setInterval` in backgrounded windows, which can silently stretch that gap past `pulsetime` and split one continuous session into two events. Every periodic tick instead calls `client.replaceEvent()` by the event's own known id, recomputing `duration` fresh from wall-clock time (`now - startedAt`) — correct regardless of how delayed a tick was, no merge-or-insert ambiguity possible.
- **`replaceEvent`/`insertEvents` both POST to the same `/events` endpoint**; whether it inserts or updates-in-place depends entirely on aw-server recognizing a pre-set `id` in the payload as "replace this." Confirmed empirically against a live server — it genuinely does update in place, but **only when the id is correct and already exists**. IDs are global across the whole aw-server instance, not scoped to one bucket — never use a placeholder/guessed id in a replace call, even in a throwaway test bucket, or you can silently clobber/relocate an unrelated real event elsewhere.
- **Only one House Simulator activity may be `running: true` at a time, enforced against AW directly, not just in-memory state.** The app no longer stops tracking when the window closes (an overnight sleep-tracking session should keep accruing time with the app shut), so a *different* activity being started is the actual moment something earlier needs closing out — and it may not be reflected in memory if the app just restarted. `startActivity()` checks AW's actual latest event, not just the local `current` variable, before beginning anything new.
- **`resumeActivity()` (called on launch) extends the still-running event's duration to real elapsed time, regardless of gap length** — it does not truncate after some timeout, and does not care if the app was closed for 10 seconds or 10 hours. This is deliberate: it's what makes leaving something "running" across an app restart meaningful (e.g. sleep tracking) instead of just a crash-recovery nicety.

### Characters: multi-character support

`characters` table (`server/characters.ts`) — each character is `{id, name, secret, awBucketId, publishToViewer, spriteName}` (plus `createdAt`, used only for ordering). The WebSocket handshake's `?secret=...` resolves to a character (`getCharacterBySecret()`), and every goal/todo/activity-tracking operation is scoped to that character's own id and AW bucket from then on — a different character's secret means a fully independent `startActivity`/goals/todos, sharing only the global room/object/activity registry. State broadcasts (`goals`/`todos`/`status`) only go to clients connected as the *same* character; `settings` was already per-device, unchanged.

`src/client/remoteState.ts`'s `characterStore`/`RemoteCharacter` carries whichever character the connection authenticated as, replacing the old hardcoded `CURRENT_USER_NAME` for the desktop app (`goals/panel.ts`'s Jacqueline-panel title reads this dynamically now).

- **`publishToViewer`** (default `false`) gates whether a character's data is included in val.town's `/api/all` blob at all — a character can exist and be fully tracked without ever being publicly visible. Jacqueline is published by default (one-time backfill for pre-existing installs, same pattern as other boolean-column backfills); any other character an admin adds starts unpublished.
- **`spriteName`** (nullable) is what a sprite-keyed overlay resolves against (see "Per-character animated overlays" under "Scene rendering" above) — e.g. `spriteName: "jacqueline"` + overlay key `"playPiano"` → `/characters/jacqueline_playPiano.png`. No sprite name set (or no matching file) falls back to `DEFAULT_SPRITE_CHARACTER`'s own art, or no overlay at all.
- The **public viewer now supports multiple characters** (see "The five things in this repo" above) — `CURRENT_USER_NAME` ("Jacqueline") is only the tie-break for which character is initially selected, not a hardcoded single-user assumption; a visitor can pick any published character via the character-picker modal.

Managed through the admin tool's Characters tab (create/rename/delete, plus editing an existing character's secret, AW bucket id, publish-to-viewer flag, or sprite name directly — changing the secret immediately invalidates any device still connected with the old one, since auth is a live secret lookup, not a cached session).

### Goals

`src/goals/types.ts` defines `Recurrence` (`once` / `daily` / `weekly` / `monthly`-by-Nth-or-last-weekday, possibly multiple occurrences) and `Goal` (activity label + target minutes + recurrence + optional `skipDates`/`createdAt`/streak fields — see "Streaks" below). `src/goals/recurrence.ts`'s `isScheduledOn()` is the one function that decides "does this goal apply today" — it's imported directly (not duplicated) everywhere that needs it, including the viewer build.

AW only measures time per activity **label**, not per goal — so the UI (`src/goals/progress.ts`) groups all of today's scheduled goals by activity label and sums their targets before comparing against tracked time, rather than tracking progress per-goal. Re-adding a goal for the same activity + identical schedule extends the existing one's target instead of creating a duplicate (so "I practiced piano, finished my 1hr goal, then added another 30min" correctly un-finishes it rather than showing two cards).

**Streaks** (`src/goals/history.ts`), recurring goals only — a "once" goal has no repetition to streak. Deliberately *not* a raw incrementing counter: `Goal.streakStartDate` ("YYYY-MM-DD") anchors the current streak, and `Goal.highestStreak` is the only actual stored number (ratchets up, never resets). `getCurrentStreakLength(goal, history)` derives the current length on demand — just a count of that goal's `completed` entries on or after `streakStartDate` — rather than storing a second number that could drift out of sync with the history log. `updateStreak()` (called from `settleGoal()`'s existing day-by-day walk, so this piggybacks on settlement rather than needing its own pass) re-anchors `streakStartDate` to *today* on every loss, not just unsets it — a loss day being its own anchor still produces a correct 0-length read afterward, since the formula only counts *completed* entries, and the loss day itself never has that outcome. Goal objects are mutated in place (same pattern as `skipGoalToday`); `settleGoalHistory()` (now `server/goalHistory.ts`) persists them via `server/goals.ts`'s `persistGoals()` only if a streak field actually changed. `goal.highestStreak` is just another field on the already-pushed `Goal` objects, so it reaches val.town for free — but a *current* streak can't be derived from that alone (it needs the full history log, which never leaves the Node server — see "no All-Time Goals in the viewer" below). That's what `/api/streaks` is for: `getTodayStreaksByGoalId()` computes current streak length for today's scheduled goals (the server has the history to do it), and `pushTodayStreaks()` pushes that map once per calendar day — same "static until the boundary changes" gating as `pushYesterdayStats`, since a streak only changes at settlement anyway. `formatStreak()` (the "Streak: 3 (best 7)" formatting, pulled out of `describeStreak()`) lives in `goals/format.ts` — a pure-formatting file split out of `goals/ui.ts` (which re-exports from it for backward compatibility) specifically so both the viewer *and* the Node server can import it without pulling in DOM-building code. `history.ts` itself is now a thin query-wrapper (`historyForGoal`/`getGoalHistory` both round-trip to the server over `sendQuery`); the actual settlement/streak-computation logic that used to live here moved to `server/goalHistory.ts` verbatim. Shown in the Goals Manage modal's row text, the desktop Dashboard's per-goal subrows, and the viewer's own Dashboard subrows (`buildDashboardBlock()` in `viewer-main.ts`, fed by `/api/streaks` + the `highestStreak` riding along on `/api/goals`) — three call sites, one `describeStreak()`/`formatStreak()` pair behind all of them.

### Three always-or-on-demand surfaces, split by time range

Status/progress UI is split across three places, deliberately divided by **time range + audience** rather than by data type (goals vs. activity):

- **Jacqueline panel** (`src/goals/panel.ts`, `buildFloatingPanel` title) — always visible, not closable, not draggable. Just "who's using the house, what they're doing right now, connection health" — no goal data here anymore. Named for the desktop app's original single-user case; the title itself is now whichever character's secret the connection authenticated as (`getCharacter().name`, see "Characters" above), not a hardcoded string. The viewer's own version of this panel titles itself after whichever character is currently selected (see "Characters"' multi-character viewer note above), updating on every character-picker switch — not hardcoded either, despite the panel's own name.
- **Dashboard panel** (`src/dashboard/panel.ts`) — always visible, not closable, draggable. **One day at a time**: a date picker (defaulting to today) drives that day's goal progress + activity breakdown; `getGoalProgressForDate()`/`getActivityStatsForDate()` branch on whether the picked day is the real current day (live, "up to now") or a settled past/future day (plain midnight-to-midnight range query).
- **Statistic modal** (`src/dashboard/statisticModal.ts`) — opened on demand from the "Statistic" button. Two tabs: **All Time** (most completed/skipped activity, all-time activity pie) and **Period** (goal progress, most completed/skipped, and an activity pie — the same three kinds of stats, just scoped to one Weekly- or Monthly-sized window at a time, picked via a mode toggle + date anchor).

This came from Dashboard and Jacqueline originally overlapping (both showing goal info) and Dashboard itself originally being one tabbed panel mixing today-only and all-time data. If a new "status" need comes up, put it in whichever of these three already matches its time range rather than adding a fourth surface or reintroducing tabs — the overlap is what got fixed here. All-time stats are only computed when the Statistic modal is actually opened (`getActivityStats()` scans a much wider AW date range) — unlike Dashboard's queries, which legitimately re-tick every 30s *while viewing today* (a past/future day's data can't change, so the interval skips re-fetching once the picker has moved off today).

**The Dashboard date picker itself is desktop-app-only** (same reasoning as "no All-Time Goals in the viewer" below): it needs an arbitrary-range AW query per picked date, and the viewer never has AW access. It does, however, apply to the app's own mobile Dashboard tab for free, since that calls the exact same `setupDashboardContent()` the desktop panel does. The viewer's own Dashboard isn't stuck on *only* today, though — it gets a Today/Yesterday hyperlink toggle instead (`.day-link` in viewer-styles.css, viewer-only — the app's date input stays the real picker). "Yesterday" is whatever the app last pushed to `/api/yesterday` (`pushYesterdayStats()`, reusing `getActivityStatsForDate()` reshaped into a plain label→minutes map, same shape `/api/status` already pushes for today) — a settled day, so unlike "today" it never needs live-elapsed-time math added. Each toggle instance (desktop panel, mobile tab) owns its own day selection independently, same as the app's own per-instance date input (`viewer-main.ts`'s `buildDashboardBlock()`).

**The Statistic modal's Period tab (free-form date picker, Weekly/Monthly) is also desktop-app-only** for the same reason, but the viewer isn't left with *only* All Time — it gets its own Period tab fed from 4 fixed windows (This Week/Last Week/This Month/Last Month) that the desktop app precomputes and pushes to val.town (see `/api/period-stats` below), instead of a free date picker. Both Period tabs share the same compute layer (`dashboard/periodStats.ts`'s `computePeriodStats()`) and the same render functions (`renderGoalList`/`renderGoalOutcomes`/`renderAllTimeActivity`) and toggle-group UI (`ui/toggleGroup.ts`'s `buildToggleGroup()`, which is why that and `.day-toggle`/`.stat-tab*` CSS had to move from app-only into shared code once the viewer needed them too) — only the picker itself (free date vs. a fixed 4-option list) and where the data comes from (live AW query vs. whatever was last pushed) differ.

### Mobile: a separate UI tree, not a reflow

Below `@media (max-width: 700px) and (orientation: portrait)` (`shared-chrome.css`), the floating panels/top-buttons/floor-buttons give way to a bottom tab bar (Home/Dashboard/Statistic/Settings) + one full-screen page at a time. **Both UI trees are always built**, in both the desktop app and the viewer — this media query is the only thing deciding which is visible, so resizing or rotating across the breakpoint needs zero JS.

`src/ui/mobileTabs.ts`'s `setupMobileTabs()` is the shared tab-bar-plus-pages skeleton (zero Tauri/AW dependency, same as `buildFloatingPanel`/`buildModal`) — it only owns tab-switching, not what's on a tab. Each entry point (`main.ts`'s `setupMobileUI()`, `viewer-main.ts`) fills the four pages with the *exact same* `setupDashboardContent()`/`setupStatisticContent()`/`buildDisplaySettingsSection()` (or the viewer's own equivalents) their desktop panels/modals already use — a mobile tab is a full-screen instance of the same content function, not a second copy of it. This is also why every Dashboard/Statistic feature added since (the date picker, the Period tab, the Today/Yesterday toggle) applies to mobile for free without any mobile-specific code — see those features' own paragraphs above.

**Home is the one tab that isn't a panel/modal content function at all** — just bare stacked status text (name/current activity/last synced, no chrome) plus one FAB, so it doesn't cover the scene. `#mobile-page-home` ignores pointer events everywhere except its own direct children (the status text, the FAB), so taps still reach the Pixi canvas underneath for looking at the house. The FAB differs per build: the app's is "Pick Action" (`setupMobilePickAction()` in `main.ts`) — a flat modal list of every activity in `ACTIVITIES`, tapping one calls `House.toggleActivity(label)` (mirrors `runAction`'s start/stop-command-plus-camera-focus logic but for a tap with no clicked object behind it — the overlay highlight itself is driven back by the server's next `status` broadcast via `applyRemoteStatus()`, same as `runAction`, see "The Node server" below) — letting you start/stop tracking without navigating to the right room/object, which matters more when screen space is scarce. The viewer's is "Leave a note" (`setupMobileMessageModal()`), a native-popup-style dialog standing in for the inline form that doesn't fit on Home — the viewer has no AW access to track anything regardless, so there's no action-picking equivalent for it.

**Room navigation (floor buttons) is dropped entirely on mobile, not just hidden** — the scene just auto-follows whatever's currently running (the same focus logic the desktop already has), and manual panning isn't worth the screen space below this breakpoint. This was a deliberate, explicit call for both the app and the viewer, not an oversight.

**Explicitly out of scope:** going further and making the mobile tabs literal `buildFloatingPanel`/`buildModal` instances (reusing chrome, not just content) was considered and declined — the win would've been smaller than the added complexity, and mobile pages already get the sizing/scrolling they need from `.mobile-page`'s own CSS (`overflow-y: auto`, full-bleed) without needing panel/modal resize semantics at all.

Building this surfaced an ordering problem worth remembering: `House`/`HouseViewer`'s constructor fires its `onRoomChange` callback synchronously for the initial room, before a caller building floor buttons *from* that callback would have anything to bind against yet. `src/ui/floorButtons.ts`'s `setupFloorButtons()` takes no arguments up front and returns `{ bindGoToRoom(fn), onRoomChange(name) }` instead — build the buttons first (a no-op `goToRoom` closure), construct `House`/`HouseViewer` passing `floorButtons.onRoomChange` as the room-change callback, *then* call `bindGoToRoom` once the instance exists. Solves the "doesn't exist yet" problem by reordering instead of papering over it with a deferred placeholder.

### Shared panel chrome (`src/ui/draggablePanel.ts`)

`buildFloatingPanel(title, { closable?, draggable?, className? })` is the one implementation behind Jacqueline's and Dashboard's header/body/drag chrome — both default to `true` for `closable`/`draggable`; Jacqueline overrides both to `false` since it always lives in the same corner and is never meant to be dismissed. It's plain DOM code with zero Tauri dependency, so **the viewer imports and calls it directly** (`viewer-main.ts`) instead of re-implementing a lookalike — the viewer's Jacqueline and Dashboard panels are the literal same component as the desktop app's, not a visually-similar copy.

Dragging is done via a dedicated grip-icon button in the header (`.floating-panel-drag-handle`), not the whole header — grabbing the title text to move the panel used to fight with just trying to read it. The grip icon itself is drawn with CSS `box-shadow` (a 2×3 dot grid), not a Unicode glyph — a glyph's availability/rendering varies by platform font, a CSS shape doesn't.

`headerExtra?: HTMLElement` lets a caller drop one arbitrary element into the header (left of the drag handle, right of the title) instead of hand-rolling a second header-ish row inside the body — the Dashboard panel's date picker uses this to live in the header, while the same content function's mobile-tab caller (no header at all there) falls back to an inline copy in the body instead. See `setupDashboardContent`'s `providedDateInput` parameter in `src/dashboard/panel.ts` for the pattern: build the control once, optionally hand it to `buildFloatingPanel` as `headerExtra`, and pass the same element into the content function so it drives the same rendering either way.

**`buildModal`'s dialog/header/body now mirror `buildFloatingPanel`'s structure exactly** (pinned header via `flex-shrink: 0`, scrolling body via `flex: 1; min-height: 0`, same `resize`-grip-vs-scrollbar `padding-bottom` fix on `.modal-dialog.resizable`) — they used to differ (the whole modal dialog scrolled as one unit, header included, and its title text/padding were plainer than the panel's). Only `width` is still legitimately per-build (`styles.css`/`viewer-styles.css` each have a one-line `.modal-dialog { width: ... }` override); everything else moved into `shared-chrome.css`'s `.modal-dialog`/`.modal-header`/`.modal-body` once the two builds' versions became byte-identical.

### Shared rendering between the desktop app and the viewer

The viewer and the desktop app need to show the *same* sections (Dashboard's Today's Goals/Today's Activity, the Statistic modal's All-Time Activity, Jacqueline's current-activity/sync-status) but get their data from fundamentally different sources — the desktop app queries AW directly, the viewer only has whatever was last polled from val.town plus client-side live-elapsed math. The fix was splitting "compute the data" (stays separate per surface) from "render the data to DOM" (shared) — and, where the UI chrome itself has no data dependency at all (the panels themselves, not their contents), just calling the exact same builder from both (`buildFloatingPanel`/`buildModal`) rather than maintaining two copies of a "static HTML + manual rendering" pattern. The viewer used to render its Jacqueline/Dashboard/Stats content into one static sidebar `<div>` defined in `viewer.html`; it now builds its panels and modal entirely in `viewer-main.ts`, the same way the desktop app's `index.html` only has `#status`/`#room-label`/`#app` and everything else is built in `main.ts`.

- `src/goals/goalGroups.ts`'s `groupGoalsForDate()` — the one goal-grouping-by-label implementation, for any date (not just today, despite the file's original name) — it also now excludes goals whose `createdAt` is after the date in question, so a past date's view doesn't show a goal that didn't exist yet back then. Before the first version of this, `goals/progress.ts`, `dashboard/panel.ts`, and `viewer-main.ts` each independently re-derived the same grouping.
- `src/dashboard/render.ts` — `buildDashboardSections()`/`renderGoalList()`/`renderActivityList()` for the Dashboard panel, `renderAllTimeActivity()` (pie + legend, capped to top 5) for the Statistic modal's activity sections (All Time and Period both), and `renderGoalOutcomes()` (the "Most completed"/"Most skipped" rows) for the same modal's All Time *and* Period tabs plus the viewer's own Period section. Called by both `dashboard/panel.ts`+`dashboard/statisticModal.ts` (fed by local AW queries / `getGoalHistory()`) and `viewer-main.ts` (fed by whatever's currently polled from val.town — `/api/status`/`/api/goals`/`/api/stats`/`/api/period-stats`/`/api/yesterday`/`/api/streaks` — plus `startedAt`-based live elapsed, same trick used elsewhere).
- `src/status/render.ts` — `renderCurrentActivity()`/`renderSyncStatus()` for the Jacqueline panel's content, plus the `CURRENT_USER_NAME` constant (now just the viewer's initial-character tie-break, not a hardcoded assumption — see "Characters" above). The desktop app doesn't use this constant for its own panel title at all, reading the connecting character's actual name from `remoteState.ts`'s `characterStore` instead. `renderSyncStatus`'s `showAw` flag is why the viewer never shows an "AW: Connected"/"Disconnected" line at all — it has no AW access full stop, not merely "currently disconnected."

**The viewer's Statistic modal has no "All-Time Goals" section** — unlike the desktop app's. The full goal completion/skip history (`getGoalHistory()`, backed by `server/stores/goalHistoryStore.ts`'s SQLite table) lives on the Node server and nothing pushes all of it to val.town; the viewer's All Time tab only ever gets activity stats (`/api/stats`). Its Period tab is the exception — it does get most-completed/skipped *outcomes*, but only ever for the 4 fixed windows in `/api/period-stats`, computed from a `getGoalHistory()` filtered to that window at push time, not the raw log itself. Don't try to fake full history by inferring completion from `/api/goals` + `/api/status` — the whole point of the history log is tracking outcomes over time, which isn't reconstructable from "what's the goal definition + today's minutes."

**CSS sharing: `src/shared-chrome.css`, imported by all three.** `styles.css`, `viewer-styles.css`, and `admin-styles.css` are three independent Vite entry stylesheets, but Vite resolves a local `@import` fine in every build — so every rule confirmed byte-identical across them (the theme palette, `.floating-panel*`, `.goal-row`/`.dashboard-row`/etc., `#floor-buttons`/`#top-buttons`, ...) lives in `shared-chrome.css` and gets `@import`ed, instead of being hand-copied into multiple files. A rule stays local to one stylesheet only when it's *legitimately* different per build (e.g. `.modal-dialog`'s width, `.settings-checkbox-row`'s margin) — if you're about to paste a new rule into more than one of these identically, it belongs in `shared-chrome.css` instead. If you add a new shared-rendering class in `render.ts`/`draggablePanel.ts`/`modal.ts` and only style it in one of the three stylesheets, check whether it should go in `shared-chrome.css` rather than get duplicated (or left unstyled in the others).

One function's scope quietly broadened for this: `getTodayMinutesByLabel()` (`src/goals/progress.ts`) used to only cover activities that had a goal attached (its one caller was the goal-progress calc). It now covers every entry in `ACTIVITIES`, because the viewer's Today's Activity list needed full parity with the desktop Dashboard's — not just whatever happened to have a goal.

### Shared persistence (`src/lib/persistedState.ts`)

`persistedState.ts`'s `createPersistedState(load, save)` (in-memory value + change-listener `Set`, backed by a `{load, save}` pair) is the one piece both the Node server's and the desktop app's state live on top of today, just at opposite ends of the same abstraction:

- **Server-side** (`server/goals.ts`, `server/todos.ts`): `createPersistedState(goalsStore.load, goalsStore.save)` where `goalsStore`/`todosStore` (`server/stores/`) are SQLite-backed `{load, save}` pairs — whole-table rewrite on `save()`, same spirit as the old JSON-blob rewrite it replaced. `server/stores/goalHistoryStore.ts` is the one exception: an unbounded, ever-growing log doesn't fit the "load it all, mutate, write it all back" shape, so it gets real indexed queries (`getInRange`, `lastSettledDateFor`, ...) instead of going through `createPersistedState` at all.
- **Client-side** (`src/goals/state.ts`, `src/todos/state.ts`, `src/settings/state.ts`): no longer backed by `persistedState.ts` or any local file at all — `@tauri-apps/plugin-fs` and the old `jsonFileStore.ts`/`goals/store.ts`/`todos/store.ts`/`settings/store.ts` are gone. Each is now a thin wrapper re-exporting `get`/`onChange` straight from `src/client/remoteState.ts`'s matching store (itself a from-scratch, WebSocket-fed lookalike of `persistedState.ts`'s `get`/`onChange` shape — see "The Node server" below), plus command functions (`addGoal`, `toggleTodo`, `updateSettings`, ...) that just call `sendCommand`.

Reuse `createPersistedState` for any new *server-side* persisted domain; a new *client-side* one should instead add a store to `remoteState.ts` and a command/query pair to `server/rpc.ts`, not reach for `createPersistedState` directly — there's no local storage on the client to back it with anymore.

### The Node server (`server/`) — the always-on backend

Introduced so every device on the home network (a Tauri build *or* a plain browser) gets full read/write access to the same live state, instead of each Tauri window independently owning its own AW connection, its own JSON files, and its own val.town push timers. One Node process, meant to run 24/7 on a home server, is now the single arbiter of AW state (no more races between two Tauri windows independently deciding to start/stop an activity) and the only thing that ever talks to val.town.

**Storage: SQLite (`server/db.ts`), not JSON files.** `migrate()` runs `CREATE TABLE IF NOT EXISTS` for every table at startup (same spirit as val.town's own `ensureSchema()` — see its migration gotcha below, which applies here too: adding a column to an existing table later needs an explicit `ALTER TABLE`, not just an edited `CREATE TABLE`). Goal/todo/settings tables: `goals`, `goal_history` (indexed on `date` — the one table that gets real range queries instead of "load everything into memory," see "Shared persistence" above), `todos`, `device_settings`, `server_config`. Also `characters` (see "Characters" above), `rooms`/`objects`/`activities`/`object_types`/`room_connections`/`floors` (see "Rooms, floors, and connections" above), and `workout_sessions`/`workout_sets` (mock-seeded, see "The five things in this repo" above).

`migrateIdsToSerial()` (also in `db.ts`, run before the `CREATE TABLE IF NOT EXISTS` block) is a one-time migration for an install that predates the rooms/objects/activities/object-types serial-id switch — detected by `rooms.id`'s declared column type (`TEXT` means pre-migration); rebuilds every affected table under a temporary name, remapping every foreign-key reference (including the `activityId`/`roomId` embedded in action JSON blobs) through old-string-id → new-integer-id maps built from each table's own rowid order, then swaps the rebuilt tables in. A no-op once `rooms.id` is already `INTEGER`, or if `rooms` doesn't exist at all (a fresh install goes straight to the final schema).

**Settings are split in two, by who should be able to change them:**
- `device_settings` (`server/deviceSettings.ts`), keyed by a `deviceId` the client generates once (`crypto.randomUUID()`, cached in `localStorage`) and sends on every connection — `scale`/`theme`/`devMode`, exactly the things a phone and a Mac might reasonably want set differently. This is `src/settings/types.ts`'s `DeviceSettings`/`DEFAULT_DEVICE_SETTINGS` (the old single shared `Settings`/`DEFAULT_SETTINGS` blob, which also held `broadcastUrl`/`broadcastSecret`, is gone).
- `server_config` (`server/serverConfig.ts`): `broadcast_url`/`broadcast_secret`/`lan_secret`, one row, hand-edited on the home server (same spirit as `aw-server.toml`'s own hand-edited config) — since the server does the val.town pushing and the WebSocket auth now, not individual devices.

**The WebSocket RPC protocol (`server/rpc.ts`, client half `src/client/remoteState.ts`):** one connection per client carries everything.
- **Commands** (`{type:"command", name, args}`) — fire-and-forget writes (`startActivity`, `addGoal`, `updateSettings`, ...). The server re-broadcasts whatever state actually changed afterward; the client never awaits a command, by design (see `House.runAction`'s comment on why camera focus happens optimistically rather than waiting for confirmation).
- **Queries** (`{type:"query", requestId, name, args}` / `{type:"queryResult", requestId, data|error}`) — request/response, correlated by `requestId`, for on-demand computed data that isn't part of the unsolicited broadcasts below (date-picker-driven progress, period stats, history for one goal, ...).
- **State broadcasts** (`{type:"state", key, data}`, unsolicited) — `goals`/`todos`/`status` sent to every client on change, `settings` sent only to the connecting client (scoped to its own `deviceId`). Sent once right after connecting (so a freshly-connected client has something to render) and again on every subsequent change.

Command/query names map 1:1 onto ordinary functions via the two dispatch tables at the top of `rpc.ts` — this is why so little of the actual logic needed rewriting when this was built: `src/aw/client.ts`, `dashboard/{stats,periodStats}.ts`'s real implementations, `goals/history.ts`'s real implementation, etc. all moved into `server/` (some verbatim, some as fresh copies — see `server/stats.ts`'s own comment for why one of them is a copy rather than a shared import) completely unchanged in substance; `rpc.ts` just wraps each one in a one-line dispatch entry.

`connectRemoteState()` (`src/client/remoteState.ts`) resolves only once the four initial state broadcasts (goals/todos/status/settings) have all arrived — not on the bare WebSocket `open` event — so `main.ts` can read `getSettings()`/`getRemoteStatus()` synchronously the moment the `await` returns, rather than racing the first broadcast.

**Auth**: a single shared secret (`lan_secret`, same spirit as the existing `broadcast_secret`) required on the WebSocket handshake (`?secret=...&deviceId=...`), so joining the home WiFi alone isn't enough to get write access. `aw-server` itself never needs its own auth story for this — it stays on loopback relative to the Node server (same machine), so it never touches the LAN at all. This is also what resolves AW's own "strongly discouraged" unauthenticated-exposure warning: not by securing AW, but by never exposing it.

**One build, two delivery mechanisms.** Once the desktop app talks to the server over WebSocket instead of calling Tauri plugins directly, its own `npm run build` output (`dist/`) is just a normal static web app — a Tauri webview loading it from disk and a plain browser loading it over HTTP are equally valid. `server/staticServer.ts` serves that same `dist/` directly off the server's own HTTP port (alongside `/health` and the WebSocket upgrade), with an `index.html` fallback for unknown paths and a path-traversal guard (this is reachable by the whole LAN). No third Vite config needed — there's only ever one build of the app itself; the server just also happens to serve it.

### Admin tool (`src/admin-main.ts`, served at `/admin/`)

A separate static site (own Vite entry — see Commands above), served by `server/staticServer.ts` alongside the game's own `dist/`. Talks to a plain REST surface under `/api/admin/*` (`server/adminApi.ts`) — traditional request/response CRUD, not the game's WebSocket RPC protocol — gated by a single shared secret (`server_config.admin_secret`, hand-edited on the server same as `lan_secret`) sent as `Authorization: Bearer <secret>` on every request. The admin tool prompts for it once and caches it in `localStorage`; a 401 clears the cached value and tells the admin to reload (self-healing, same reasoning as the game's own connection form) rather than silently failing.

Five tabs: Characters, Activities, Object Types, Sprite Overlays, Rooms. Every tab follows the same conventions, converged on after a few iterations:
- **Modal-based add/edit** (`buildModal`), not always-editable inline table rows — a plain read-only table with Edit/Delete buttons, Edit opening a small modal with the actual fields. Applies to Characters, Activities, Object Types, and Sprite Overlays alike.
- **Sprite Overlays tab**: manages the named, reusable `SpriteOverlayDef` rows (`server/spriteOverlays.ts`'s `sprite_overlays` table — `spriteKey` + optional `frameCount`/`frameDurationMs`) that Object Types reference by id instead of embedding an inline overlay blob each — see "Per-character animated overlays" under "Scene rendering" above. The Object Types tab's own editor just picks one of these by id (hint text points there) and sets its own `overlay_offset_x/y`, since the same overlay can be positioned differently per object type.
- **Never show a raw id to the admin** — tables/dropdowns show names; the id is only ever what gets submitted on save (a `<select>` option's `value` is the id, its visible text is the name). Rooms/objects/activities/object types all have server-assigned serial ids now (see "Rooms, floors, and connections" above), so there's nothing meaningful to show anyway — no "Add Room"/"Add Object" form has an id input.
- **Rooms tab**: Floors section first (level/label/base-room, add/edit/remove — edit swaps the base-room cell for a `<select>` in place rather than a separate modal), then one sub-tab per floor (highest level first) plus an "Unorganized" tab for rooms unreachable from any floor's base room. Each floor's sub-tab shows its connection tree (`buildFloorTree()`, a plain indented `<ul>`, not a graphical chart) above a plain room list (name/size/object count, Edit/Delete). **The tree is what manages connections** — clicking a room's name in the tree opens that room's connections editor directly; the per-row list below is purely for editing the room itself (name, cols/rows resize — clamped to a 1×1 minimum, no bounds-checking against objects — the four wall-visibility checkboxes, the `visible` checkbox, and its objects). Unorganized rooms have no tree to click (nothing to draw one from yet), so they're the one case that keeps a "Connections" button on the row itself — the only way to attach a brand-new room to anything.
- **Room object editor**: a staged local draft (nothing written until Save), live preview reusing `AdminPreviewRenderer` (the exact same `SceneRenderer` the game/viewer use, with click-to-select and click-to-place-on-the-grid layered on top — see `scene/adminPreview.ts`). x/y edits move the existing sprite directly (`moveObject()`) rather than rebuilding the scene, specifically to avoid a "blip" on every keystroke; type/enabled/resize changes do a full rebuild since the sprite/room itself actually changes. A brand-new, not-yet-saved object placement has no id (`ObjectPlacementWire.id?: number`) until Save persists it — the draft/diff logic keys new-vs-existing off that rather than any admin-chosen value.

**Not done here, deliberately**: bounds/collision validation (object positions vs. room size, connectedTo cycles beyond a "does this reference a real room" check — see `resolveRooms()`'s own comment on why cycles stopped being an error) — same "hand-coordinated, no automatic validation" spirit as the rest of this system.

### Broadcasting: why val.town is deliberately dumb

**This section describes val.town's own schema and push/poll design, which is entirely unchanged by the Node-server migration above — only *who* does the pushing changed.** Every `pushX()` function named below now lives in `server/broadcast.ts` and is called from `server/index.ts`'s own startup + `setInterval`s (or from `server/rpc.ts` right after a `startActivity`/`stopActivity` command), instead of from `main.ts`'s timers running inside whichever Tauri window happened to be open. This is strictly an improvement for the reasons "The Node server" above lays out (one 24/7 process instead of "only while some window is open") — it does not change what gets pushed, how often, or how the viewer consumes it. Treat "the desktop app pushes X" below as "the Node server pushes X" throughout; the sentences are kept as originally written because the *design reasoning* (what's pushed, why, and on what cadence) hasn't changed at all.

**Every blob below is now pushed per-character**, not just for Jacqueline — `pushStatus(characterId)`/`pushGoals(characterId)`/`pushStats(characterId)`/etc. each run once per character with `publishToViewer` set (see "Characters" above), and val.town stores/keys each by character id (`valtown/houseSimulatorStatus.ts`'s schema). The viewer's `/api/all` fetches every published character's full blob set in one request (one directory listing doubling as the character picker's data source), while the individual `/api/status`/`/api/goals`/etc. endpoints remain single-character for any caller that only needs one. This per-character keying is additive to everything below — the push cadence, caching, and what each blob contains are otherwise unchanged from the single-character design.

The viewer can never reach the local `aw-server` directly — it's a separate static site, possibly on a different machine. So *something* local has to combine goal targets with tracked time and publish the result; `val.town` only stores and forwards independently-pushed blobs, each on its own cadence:

- **Goal definitions** (targets + schedules, not progress) — pushed whenever goals change (`onGoalsChange` → `pushGoals()`), independent of activity changes, so editing a goal reaches the viewer immediately instead of waiting for the next activity switch.
- **Today's tracked minutes per activity label**, *excluding* whatever's currently running — pushed on activity change (`onActivityChange` → `pushStatus()`) and once at startup. Nothing is re-pushed on a timer.
- **All-time per-activity totals + rolling daily averages** (`pushStats()`, backing `/api/stats`), **the 4 fixed This Week/Last Week/This Month/Last Month windows** (`pushPeriodStats()`, backing `/api/period-stats`), **yesterday's tracked minutes per label** (`pushYesterdayStats()`, backing `/api/yesterday`), and **today's scheduled goals' current streak length, by goal id** (`pushTodayStreaks()`, backing `/api/streaks`) — all four scan more AW history (or, for streaks, more of the history *log*) than `pushStatus`'s today-only query, so they share one slow hourly timer (startup + `setInterval`, see `server/index.ts`'s `runStatsPushes`) instead of piggybacking on activity/goal changes. None of the four get their own separate cadence: simpler than tracking day/week/month boundaries directly in the scheduler, and This Week/This Month genuinely want hourly freshness since they change through the day. The *static* ones — Last Week, Last Month, yesterday, and today's streaks — instead self-skip the expensive part once nothing could have changed: `pushYesterdayStats`/`pushTodayStreaks` each track which "today" they last successfully pushed for and no-op on repeat calls within the same day (only advancing that tracker on a successful push, so a transient val.town outage still retries); `computeFixedPeriodStats()` caches Last Week/Last Month in memory keyed by that window's own start date, and only redoes the AW query once the cached start date no longer matches. All these caches are in-memory only, not persisted — an app restart recomputing once is a reasonable resync, not something worth avoiding. Either way the full push still happens every hour (val.town doesn't need its own staleness logic); only the local AW querying is what gets skipped.

For today's goal progress, the viewer joins the first two blobs itself — computes "is this goal scheduled today," sums targets by label, and adds the *live* elapsed time for whichever label matches the currently-running activity (the same `startedAt`-based client-side math as its "Running for X" clock). This is why val.town never needs to recompute anything when a goal is edited or time passes: both halves are always independently fresh, and the join is cheap and stateless on the client. The period stats are different: val.town stores exactly what `computeFixedPeriodStats()` already computed app-side (goal progress + outcomes + activity totals per fixed window) — there's no further joining for the viewer to do, since there's no live "running" session's elapsed time to merge into a past or fixed-boundary window the way there is for "today."

**The house layout itself** (activities/object types/rooms incl. objects+connections/floors — see "Rooms, floors, and connections" above) is also pushed, as one combined blob (`pushHouseLayout()`, backing `/api/house-layout`) — without this, the viewer has no way to see an admin-tool edit at all, ever, since it has no WebSocket connection (unlike the desktop app, which gets this same data pushed once per connect over RPC) and nothing else pushes it anywhere. Deliberately **not** on the hourly timer or on any per-edit hook: pushed once at server startup, and otherwise only when the admin tool's own "Sync to viewer" button is clicked (`POST /api/admin/sync-house-layout`) — admin edits are infrequent and usually come in a burst of several fields/rooms in a row, so an explicit sync once the admin is actually done beats either polling or re-pushing after every single mutation. The viewer fetches this once at its own startup, before building the scene at all (falling back to its own build's `STATIC_*` data on a fetch failure), not on the regular status/goals poll interval — there's no live "did the layout just change" signal to react to, so a plain page reload is what actually picks up a new sync.

**A real backend (with actual computation/joins) was deliberately rejected** for this — see the conversation history around "do we need a second backend" if resurrecting that question; the conclusion was that AW-local-only data makes a smarter backend not actually solve anything a dumb relay doesn't.

**Dead end, don't retry:** serving the actual Pixi-rendered viewer directly from val.town (so val.town alone would be the whole public site, no GitHub Pages needed) was tried and reverted — val.town caps a val's own source at **80,000 characters**, and a bundled Pixi app is several hundred KB even minified. Not a tuning problem; the viewer needs real static hosting (GitHub Pages).

**Schema migration gotcha:** val.town's `ensureSchema()` uses `CREATE TABLE IF NOT EXISTS`, which is a no-op once a table already exists in the live val's database — it does **not** retroactively add new columns. Any future change to an existing table's shape needs an explicit `ALTER TABLE ... ADD COLUMN` (wrapped in a `.catch(() => {})`, since it only fails if the column's already there) alongside updating the `CREATE TABLE` statement for fresh deployments. This bit us once already (a renamed column silently never existed on the live table, so every status push was failing with no visible error — see `pushStatus`'s `res.ok` check below).

**Never trust `fetch()` resolving as "it worked."** `fetch()` only rejects on network-level failures — an HTTP error response (e.g. the 500 from the schema bug above) resolves completely normally. `server/broadcast.ts` explicitly checks `res.ok` and tracks last-success/last-error in memory; `src/broadcast/client.ts` is now just a query-wrapper that asks the server for that health info (`getBroadcastHealth()` → `sendQuery("getBroadcastHealth")`) rather than tracking it itself, surfaced the same way as before — the "VT: Synced ..." half of the Jacqueline panel's status line (the one place in the app that's always visible without opening devtools) — and, symmetrically, as the viewer's own "VT: Synced ..." line for its last successful *poll* rather than push (see "Shared rendering" below).

### GitHub Pages deployment (`.github/workflows/deploy-viewer.yml`)

Builds and deploys only `dist-viewer/` on every push to `main` — the desktop app's own source is never published. Two things that would silently break if "fixed" without understanding why:

- `vite.viewer.config.ts` sets `base: "/jacqueline-house-simulator/"` — GitHub Pages serves a project repo from that subpath, not domain root. Every texture path in `rooms.ts` is a root-relative string (`/objects/piano_base.png`) baked in long before Pages was a consideration; `src/scene/renderer.ts`'s `assetUrl()` helper routes every one of them through `import.meta.env.BASE_URL` so they resolve under the subpath. (`BASE_URL` is `/` for the Tauri app's own build — this is a no-op there.)
- `npm run build:viewer` renames the build output from `viewer.html` to `index.html` as a second step. Can't just name the *source* file `index.html` — the Tauri app's own entry already owns that name at the repo root — but Pages needs `index.html` specifically to serve the bare directory URL (`/jacqueline-house-simulator/`) instead of 404ing while `/jacqueline-house-simulator/viewer.html` works fine.

### iOS (sideloaded, personal use — `src-tauri/gen/apple/`)

This repo was already on **Tauri 2** (`tauri = "2"` in `Cargo.toml`, `@tauri-apps/cli@^2`) when mobile support was added, and `src-tauri/src/lib.rs`'s `run()` already had `#[cfg_attr(mobile, tauri::mobile_entry_point)]` from the original `create-tauri-app` scaffold — so there was no Tauri 1→2 migration to do, and nothing about "the desktop app is a thin WebSocket client" (see "The five things in this repo" above) needed to change for iOS: the same `dist/` build, the same connection-form-on-first-launch flow, runs as-is inside the iOS webview.

**One-time machine setup** (already done on Jacqueline's Mac as of this writing, documented here for a future reinstall or a second machine):
```bash
rustup target add aarch64-apple-ios aarch64-apple-ios-sim x86_64-apple-ios
brew install cocoapods   # `tauri ios init` tries to install this via `gem`, which needs sudo — brew doesn't
npx tauri ios init --ci  # generates src-tauri/gen/apple/ (an xcodegen-driven Xcode project), also brew-installs xcodegen + libimobiledevice
```
`--ci` skips the interactive prompts (team selection, etc.) — fine for this generation step since signing is set up later, by hand, in Xcode itself (see "Remaining manual steps" below).

**Gotcha: `xcode-select`'s active developer directory defaulting to the Command Line Tools, not Xcode.app itself**, even with a full Xcode install present in `/Applications`. `xcodebuild -version` fails outright until this is fixed for the current shell — and setting `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` alone wasn't sufficient, because `tauri ios build`'s own `xcodebuild` invocation resolves the `xcodebuild` binary via `PATH` first rather than consistently deferring to `DEVELOPER_DIR`. The fix that actually works is putting Xcode's own toolchain directory *ahead* of everything else on `PATH`, in addition to `DEVELOPER_DIR`:
```bash
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
export PATH="/Applications/Xcode.app/Contents/Developer/usr/bin:$HOME/.cargo/bin:$PATH"
```
(`$HOME/.cargo/bin` is there too since a fresh shell doesn't have `rustc`/`cargo` on `PATH` either unless `rustup`'s own shell init has run — same two-line export needed before any `cargo`/`tauri` iOS command.) Permanently fixing `xcode-select` system-wide (`sudo xcode-select -s /Applications/Xcode.app`) would also work but needs an interactive sudo password, so the per-shell export is the repeatable, non-interactive path.

**Building for the Simulator** (no Apple ID / code signing needed at all — this is the resumable, fully-automatable half of iOS support):
```bash
npx tauri ios build --debug -t aarch64-sim --no-sign --ci
```
Produces `src-tauri/gen/apple/build/arm64-sim/House Simulator.app`. Confirmed working end-to-end: `xcrun simctl boot <device-id>` → `xcrun simctl install <device-id> ".../House Simulator.app"` → `xcrun simctl launch <device-id> com.jacqueline.housesimulator` → `xcrun simctl io <device-id> screenshot out.png` showed the real app running — the mobile-breakpoint UI (see "Mobile: a separate UI tree" above) and the "Connect to House Simulator server" form (`src/client/remoteState.ts`) rendering correctly, same as a phone-width browser window. Getting past that form needs the real `lan_secret` (hand-set in `server_config`, not something to guess or commit), so actually reaching the rendered house scene is the one thing left for Jacqueline to do interactively — everything about the iOS *shell* itself (Rust binary, webview, JS bundle, asset loading, mobile layout) is already proven working.

**`src-tauri/gen/apple/` is meant to be committed**, not regenerated per-machine — `src-tauri/.gitignore` already excluded `/gen/schemas` (auto-regenerated capability schemas) from before any mobile work started, but deliberately left `/gen` itself untouched, so `/gen/apple` — the actual Xcode project, including signing-relevant files like `project.pbxproj` — is tracked. The generated project has its own narrower `gen/apple/.gitignore` (`xcuserdata/`, `build/`, `Externals/`) that keeps user-specific Xcode state and build output out, which is the right split: commit the project, not its build artifacts or Jacqueline's personal Xcode UI state.

**Remaining manual steps (Jacqueline, on her own Mac, in Xcode — not scriptable, needs her Apple ID):**
1. Open `src-tauri/gen/apple/tauri-app.xcodeproj` in Xcode.
2. Xcode → Settings → Accounts → sign in with her personal Apple ID (a free account is enough for local sideloading, no paid Developer Program needed).
3. Select the `tauri-app_iOS` target → Signing & Capabilities tab → under "Team," pick her personal team (created automatically once she's signed in) → let Xcode auto-manage signing.
4. Connect her iPhone via USB (or same-WiFi if she's set up wireless debugging) → on the phone, trust the computer if prompted, and enable Developer Mode under Settings → Privacy & Security → Developer Mode if this is its first-ever sideloaded app.
5. In Xcode's device/scheme picker (top toolbar), select her iPhone as the run destination instead of a Simulator.
6. Hit Run (▶). First launch on-device will show an "Untrusted Developer" prompt on the phone — Settings → General → VPN & Device Management → trust her Apple ID's developer profile, then relaunch from the Home Screen.
7. On the connection form (same one shown in the Simulator screenshot above), enter her LAN server address (`ws://<mac-lan-ip>:4000`) and the `server_config.lan_secret` value.

After that first Xcode-driven run, reinstalling updates can go back to the headless `tauri ios build` path (now with signing available, so without `--no-sign`) if she ever wants to script future rebuilds — the manual steps above are a one-time trust/signing setup, not a per-build requirement.
